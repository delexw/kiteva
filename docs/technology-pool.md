# Technology inventory

[English README](../README.md) · [中文 README](../README.zh-CN.md) · [Architecture](architecture.md)

This page lists everything Kiteva knows about, depends on or ships. It's long on
purpose. The README has the short version.

Three different things are easy to mix up, so they are kept apart here:

1. **The technology pool** (`src/shared/technology-pool.ts`). These are recommendations
   attached to Motion Graphics in the catalog. An entry being in the pool doesn't mean
   it's installed, vendored or even an npm package.
2. **What ships in this repository.** That covers Kiteva's original code, the catalogs and
   reviewed previews, one startup-installed authoring skill (Anatomy), and npm dependencies
   declared in `package.json`.
3. **What you install yourself.** Node, a Chromium browser, `ffmpeg`/`ffprobe`, Python
   for local speech, optional desktop tools, and model weights. Model weights are never committed to Git.

Counts reflect the current source; native Windows dependencies were added on 2026-10-18.

## Who does what

These are separate jobs. A single library can do more than one, but Kiteva records which job it's doing.

| Responsibility                                       | Meaning                                                                    | Examples                                                                                                                                                                                                           |
| ---------------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Visual construction** (pool role `style_renderer`) | Draws the picture: geometry, materials, type, textures                     | [SVG](https://developer.mozilla.org/en-US/docs/Web/SVG), [Three.js](https://threejs.org/docs/), [PixiJS](https://pixijs.com), [Rough.js](https://github.com/rough-stuff/rough/wiki)                                |
| **Motion engine** (`motion_engine`)                  | Moves things over time: easing, transitions, simulation                    | [GSAP](https://gsap.com/docs/v3/), [Motion](https://motion.dev/docs/animate), [Matter.js](https://brm.io/matter-js/docs/) (recommended, not installed)                                                             |
| **Render pipeline** (`render_pipeline`)              | Assembles scenes against seekable time, mixes audio, validates and exports | [HyperFrames](https://hyperframes.heygen.com/developers), [Multiplane](https://github.com/LBEILC/Multiplane), [Remotion](https://www.remotion.dev/docs/) fallback, [FFmpeg](https://ffmpeg.org/documentation.html) |
| **Built-in agent tool**                              | A capability Kiteva hands to the model during a turn                       | `reference_browser` (inspect, click, screenshot) and `capture_video`, browser control with [Puppeteer](https://pptr.dev), recording with [OpenScreen](https://github.com/getopenscreen/openscreen)                 |
| **Startup-installed authoring skill**                | Reference instructions plus a drawing kit the model may read               | [Anatomy](https://github.com/wheresryan22/anatomy)                                                                                                                                                                 |

The catalog's production policy puts it this way: the pipeline must not decide or simplify the visual
style. HyperFrames is the first choice for composition and export, and Remotion is the conditional fallback.

## The startup-installed skill: Anatomy

Kiteva registers one upstream skill and installs or updates it at server launch. Its upstream files are not tracked in this repository.

|                    |                                                                                                  |
| ------------------ | ------------------------------------------------------------------------------------------------ |
| Upstream           | [wheresryan22/anatomy](https://github.com/wheresryan22/anatomy)                                  |
| Installed revision | Current upstream default-branch commit, recorded in `skills/anatomy/current.json`                |
| Files              | Downloaded files, each with a SHA-256 hash in `skills/anatomy/current.json`                      |
| License            | MIT, © 2026 Ryan. The upstream `LICENSE` is kept unchanged in `skills/anatomy/<revision>/`       |
| Kiteva's own files | `src/server/agents/bundled-skills/anatomy.ts` (registration), `anatomy-prompt.ts` (instructions) |
| Used for           | Detailed isometric technical illustrations and mechanisms. Its 3D mode is beta                   |

Before every file-enabled Claude or Codex turn, Kiteva checks each hash and copies the files to
`.agents/skills/anatomy` inside that turn's workspace. Text-only turns get no skill files.

- **Claude**: the [Claude Agent SDK](https://github.com/anthropics/claude-agent-sdk-typescript) loads
  the workspace's `.agents` folder as an app-owned local plugin called `bundled-authoring`. It enables
  only `bundled-authoring:anatomy` through the SDK's `skills` option and includes the native `Skill`
  tool. User and project settings sources are empty (`settingSources: []`). If the startup event
  doesn't list the skill, Kiteva stops the turn.
- **Codex**: the [Codex SDK](https://github.com/openai/codex/tree/main/sdk/typescript) has no plugin
  step here. It gets the same written instructions and reads the same local files with its normal coding tools.

Anatomy is optional. The model uses it when a scene suits it or when you ask for it, and it isn't tied
to any Motion Graphic. It doesn't replace the renderer. For video, its interactive examples have to be
driven from composition time and checked with forward, backward and direct seeks. Downloads run once at launch, never inside provider turns. Internet access is required for the first installation. Node.js downloads the upstream ZIP directly over HTTPS; no Git CLI, skills CLI, GitHub API or access token is required. Failed updates retain the last verified revision; if none exists, the app opens but creative tasks stop with a setup message. No upstream installation scripts are executed.

## Built-in browser tools

Kiteva inspects references locally or controls an isolated worker browser with [Chrome](https://developer.chrome.com/blog/chrome-headless-shell) (Chrome Headless Shell or another [Chromium](https://www.chromium.org) you point it at)
through [`puppeteer-core`](https://pptr.dev). It never uses your personal browser profile.

The existing eight tools are `inspect_page`, `click_control`, `capture_screenshot`,
`capture_video`, `fill_control`, `upload_files`, `scroll_page` and `wait_for_view`.
Seventeen additional tools expose the remaining browser capability groups:

| Tools                                                   | Capabilities                                                                                                                                |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `browser_navigate`, `browser_tabs`, `browser_frames`    | History/reload, isolated tabs/popups and frame selection                                                                                    |
| `browser_element`                                       | State/bounds, selectors/open shadow DOM, focus, hover, scrolling, option selection, checked state and editable fields                       |
| `browser_pointer`, `browser_keyboard`                   | Move/click/double/right click, drag, wheel, touch, keys, shortcuts and text entry                                                           |
| `browser_dialog`, `browser_wait`                        | JavaScript dialogs and condition-based waits                                                                                                |
| `browser_evaluate`, `browser_diagnostics`               | Page-context JavaScript, DOM/accessibility, console/errors, network events, response bodies and metrics                                     |
| `browser_session`, `browser_network`, `browser_emulate` | Isolated cookies/storage/permissions, offline/cache/blocking/headers, network delivery limits, viewport/device/environment and CPU settings |
| `browser_capture`, `browser_downloads`                  | Full-page/element PNG, PDF and managed downloads into job assets                                                                            |
| `browser_media`, `browser_debug`                        | Media playback/seeking, tracing, coverage, heap snapshots, script inspection and debugger controls                                          |

Descriptions, argument schemas and planning permissions have one owner:
[`reference-tool-registry.ts`](../src/server/requests/reference-tool-registry.ts). The MCP server
publishes these contracts directly; local execution and the desktop worker validate the same
requests. Planning exposes only the tools marked read-only; demo execution exposes all 25.
Page evaluation has browser globals, not Node filesystem APIs. Login, credential entry,
real account changes remain prohibited by agent guidance. Local mode uses Chrome's native
networking for normal app requests, including POST/PUT/PATCH/DELETE and binary uploads;
URL validation and supplied-origin navigation checks remain. Hosted mode retains the
validated fetch layer and GET/HEAD restriction. Upload files must
stay inside the job workspace (1–8 files, at most 10 MiB each). Condition waits are bounded
at 30 seconds. Diagnostic output is bounded at 64,000 characters. Local network throttling
uses Chrome's native controls; hosted throttling applies to buffered response delivery.

Mouse actions feed the existing OpenScreen pointer track. Cursor smoothing is fixed at 0.15.
After site exploration, the main planner storyboards component focus, minimal zoom and wide
intervals; full components and labels must fit. Native takes start wide and export preserves
the reviewed zooms without adding automatic click zooms. Native editing and review remain
owned by the copied OpenScreen workflow.
Stop a take before changing tabs,
viewport or paused debugger execution. Capture is independent of the renderer, Motion Graphic
and narration setting: HyperFrames uses recorded video; Multiplane uses a deterministic frame
sequence extracted from that recording. Neither substitutes screenshots for requested footage.
`capture_video` has no Kiteva take-count, call-count, recording-duration or output-size cap, with native
OpenScreen review/edit/export. It uses the configured desktop worker, or the current machine
when no worker URL is set. See [worker setup and verification status](openscreen-worker.md).

## The technology pool (92 entries)

Status values:

- **Installed, direct dependency**: declared in `package.json` and present after `npm ci`.
- **Part of installed `three`** / **Included in installed `gsap`**: a component or plugin inside a direct dependency.
- **Technique written on installed …**: a rendering approach the agent writes by hand using an installed library.
- **Present only as a transitive package**: it happens to be in `node_modules` because another package
  depends on it. Don't rely on it. It may disappear when dependencies change.
- **Recommended only, not installed**: listed so the model knows the idea exists. Generation can't install
  packages or reach the network, so it has to use an alternative or report that the capability is unavailable.
- **External …**: not npm packages and not bundled.

"What it does" and "Constraints" are shortened from the first sentence of each entry's own `purpose` and `selection_guidance` in the source. A few still name the Motion Graphic they were first written for. Full text is on the app's **Explore → Technology pool** window.

Generated compositions see the app's `node_modules` read-only. Each job workspace also gets copies of
GSAP, Three.js and Pica under `vendor/`.
